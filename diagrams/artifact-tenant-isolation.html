ADR-005 · Architecture

Where tenant isolation is enforced — and where it quietly isn’t

The demo account should see one batch. There are two ways it can show one, and only one of them means anything.

Running the assertion

  1. Sign in as demo@tvicams.app.
  2. Open /dashboard — not /billing. Billing’s mock fallback made zero rows indistinguishable from all rows until ADR-005 removed it, so a stale deployment there hides the very failure this checks for.
  3. Confirm the “Data as of” stamp is present before counting anything.
  4. Expect exactly one batch: DEV-AKB-001.

Five batches is ambiguous, not automatically a regression. On the fallback path the dashboard hands a viewer the full unscoped mock set, and an unresolved role also defaults to viewer. Since ADR-005 makes demo a viewer, it is precisely the role that sees every school’s mock data when the snapshot isn’t ok. Without the stamp, the count proves nothing either way.

Five, not three. An earlier count used DEV-[A-Z]+-[0-9]+, which cannot match J3ED — the digit falls outside [A-Z]+ — so both J3ED rows were dropped.

Grants after the seed

One membership each. can_access_tenant grants on any membership and ignores is_default, so a second row merges tenants into one unscoped list rather than making them switchable.

Why the verification query can’t settle it

The seed’s own check joins through profile_tenant_memberships, so a tenant with no member never appears in its output. J3ED has no member by design — which is exactly why the miscount above went unnoticed for as long as it did. The assertion has to be run in the app, signed in, not in SQL.
